# Staging deployment

The [sandbox proposal](../docs/aws-sandbox.md) records the expected resources and approval inputs. Validate Terraform without an AWS backend using `terraform -chdir=infra/staging init -backend=false` followed by `terraform -chdir=infra/staging validate`. After account approval, the owner initializes the approved S3 backend, saves and reviews a plan, and applies the reviewed plan with the staging bootstrap identity.

The bootstrap owner uses the RDS bootstrap secret to create a separate database login that owns only the `fleet` database and its schema. Download the regional RDS CA bundle and create the `fleet-rds-ca` ConfigMap in the `fleet` namespace with the file key `bundle.pem`. Use the RDS endpoint hostname and `sslmode=verify-full&sslrootcert=/etc/fleet/rds/bundle.pem` in the connection string. Store it and the three public Auth0 settings in the `fleet-runtime-secrets` Kubernetes Secret. Deploy from the approved operator network using a short-lived AWS identity mapped to the cluster. The publisher role has ECR access and no EKS access. [RDS certificate verification](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.SSL.html)

Register an Auth0 SPA and an RS256 API for the staging hostname. Use Auth0's default access token profile, which supplies the `azp` claim. Allow only the exact HTTPS origin for callbacks, logout and web origins. Provision each reviewed `(issuer, subject, principal_id)` mapping in `hosted_identities` and review the matching database grants. Auth0 subjects are case-sensitive. Provision different users for the partner, approver and operator walkthroughs.

Before enabling publication, the repository owner sets its OIDC subject template to `{"use_default":false,"use_immutable_subject":true,"include_claim_keys":["repo","ref","workflow_ref","event_name"]}` using the repository OIDC customization endpoint. Confirm the resulting subject matches the Terraform trust policy, including the workflow file path and the `workflow_run` event. Limit direct write access to trusted maintainers while the repository's plan lacks required branch protection. [GitHub OIDC customization](https://docs.github.com/en/rest/actions/oidc)

Set `FLEET_AWS_REGION`, `FLEET_ECR_REGISTRY`, and `FLEET_PUBLISH_ROLE_ARN` after provisioning. Enable the publisher with `FLEET_RELEASE_ENABLED=true` for the approved window. On a passing main push, it stores the source, ECR digests and matching scan reports in a GitHub artifact. Find the successful **Publish immutable release** run for the reviewed commit, get the artifact's `sha256:…` digest from the GitHub Actions API, and download the original ZIP from that artifact's archive endpoint. [GitHub artifact metadata and download](https://docs.github.com/en/rest/actions/artifacts)

Run `python scripts/prepare-promotion.py staging <release.zip> --source <reviewed-sha> --digest <github-artifact-digest>` to verify the archive and generate the staging overlay. Review with `kubectl kustomize deploy/release-staging` before applying with the staging context. Record the verified archive digest in the staging sign-off after smoke tests. To prepare production, use the same ZIP, source, and recorded digest with `prepare-promotion.py production` and a separately approved production identity. Retain the deployed and rollback digests in ECR while they are in use. The worker, relay and projector reuse the API digest.

For external staging access, use the approved AWS load balancer integration. Set `aws-load-balancer-ssl-cert` to the reviewed ACM certificate ARN and apply `staging/ingress.yaml` after the base is ready. Register the chosen DNS name only after the TLS endpoint is healthy. Use the same immutable manifest when preparing production and select the production cluster with a separate human release identity.

The single Kafka broker can restart and reuse its disk. It has no replica and cannot provide availability after a disk or Availability Zone loss. PostgreSQL stores the accepted observations. Preserve it and reconcile unprocessed events before replaying after broker loss.
